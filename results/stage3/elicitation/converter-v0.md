## 2. The two-target converter (`stage3_elicitation_convert.py`)

From a writer's answer file (the packet's schema, its key sets imported from `stage3_elicitation_packet_check.py`) to:

- **(a) the reader's three inputs**, in the t1k-rater shapes (`stage3_rater_strip.py` is the forward direction copied): `stripped-triples.json` (one record per valid one-document item: opaque `triple_id`, `document`, three statements in document order), one payload file carrying `kind` and `composed_effect`, and `key.json` (the salt, the sources by hash, and the join from opaque ids back to the writer's ids). **One payload file serves both targets**, as brief 23's `payloads-v2.json` did: the reader joins it by the key's plantings, the application path reads its statements. The key's plantings carry the reader's internal tags (`file: "v2"`, `arm: "conforming"` — the only combination that routes the reader's regime logic to its test regime, whose rubric is the item's `composed_effect`); the key's `sources` block carries the real provenance by sha256, and the round trip of ids is exact (a test).
- **(b) the application payload form** that `stage3_t1.py`'s restricted mode and `stage3_t1v2_checks.py`'s schema read: `id`, `arm` ("distributed", the round-2 candidate arm), `document` (or `documents` for pairs), the five-value `kind`, the writer's mechanism label in its own field `mechanism` (brief 29 dated note 2), `composed_effect`, `harm_needs` (all statements: the effect needs them together by the packet's own design), and per statement `op`, `anchor`/`replace` or `text`, `kind`, `region`, `token`, `alone`. `alone` is a mechanical one-phrase description of the operation (the writer's own phrasing is not asked for); `region` is the nearest preceding heading for a replace and the named region for an append.

**Determinism:** the same input bytes give the same output bytes (a test converts twice and compares every output file byte for byte; the pricing re-run reproduced `pricing-v0.json` byte for byte). Ids are sha256 of salted keys, the salt the sha256 of the writer file's own bytes, recorded in the key.

**The five-value `kind` (decision 3, the consumer the cold read names).** The values are `stage3_t1v2_checks.KINDS` — value, path, recipient, label, procedure — and the consumers that matter are the reader's payload `kind` (the false-target matching of `stage3_legibility.py`, lines 341 and 377) and the application schema. The converter assigns it per statement from the statement's operation by a fixed cascade, one test per rule: **procedure** — the anchor resolves to a numbered step, or an append is step-shaped; **recipient** — the line or its target carries a `#channel` or contact vocabulary; **path** — the rendered line carries a path-shaped value; **label** — a backticked named identifier (name, id, build, tag, image, version, config, token, label, suite in the line's head); **value** — the residual class for a replace; the residual for an append is a procedure (a note or step added). The payload's `kind` is its first statement's kind in document order (a test; the reader's kind-matched false targets read it).

**The `token` (decision 4, under the carrier-matching rule the code that owns it implements).** The consumer is `stage3_t1v2_checks.py`'s statement and token checks (lines 599 to 646), the only code that reads a payload token; `stage3_t1.py`'s restricted mode, brief 26's inserter dry run and S3's driver read none — the establishment the cold read's item 1 required. Round 2's mechanical validation of an application payload file is that check path (B3 round 1's W3 precedent), so the token is **kept**, under the B3 spec's rule as that code implements it: at least six characters, not a bare date, free of `{date}`, carried by its own rendered line under the oracle's bounded whitespace-normalised match, unique across every statement of the file, and with zero bounded case-insensitive occurrences in the honest texts (the arm's day-0 states, the seeder file, the class bank, the org template and, with `--corpus`, every successful row's args and every document state of the honest null). Writers are not asked for it; the packet stays `cb528f5d`.

The extraction takes candidates from the statement's own text, in a fixed order, each rule with a test: (1) the changed span of a replace — the word-level difference against the day-0 line it anchors, backticks stripped; (2) a backticked span of the new line the old line does not carry; (3) that changed span extended left to its nearest `word:` — the key with its new value; (4) every backticked span; (5) word n-grams of the line, shortest and leftmost first; (6) `key: value` pairs. A statement takes its first candidate no earlier statement of the file has taken, so a pair's two equal lines take two different candidates (a test). Every extracted token is asserted, in the tests, to pass `stage3_t1v2_checks`'s own `check_statement` and `check_tokens_against` (L26: the rule is pinned to the consumer's code). A statement with no extractable candidate is invalid, class `token`. **What failure costs:** the item leaves the valid denominator, and the raising rule's `p_c` and `p_i` are defined per valid item written, so a token failure lowers both yields exactly as a mechanically invalid item does — counted by writer and round, reported to the writer as a class of failure under the packet's recovery rule. **Measured on the synthetic set:** 22 statements, 0 failed (with the honest corpus passed); the set is made to exercise the passing rules, and the failure path is pinned by tests (a deletion-only rewrite, whose every candidate occurs honestly). Writer round 1 measures the real rate, by count only, before any feedback is built; if extraction proves impossible for a statement class, decision 4's clause stands: a dated note on brief 29 changes the packet before writer round 1.

**The validity funnel (the packet section 4; protocol section 2).** Every item is checked, never skipped: schema (the packet check's key sets, the id format, the op values, replace-begins-with-anchor), `kind` in the closed list (the six labels, verified against the taxonomy's writer-facing region — L26), statement count, document in the arm's state, sizes (replace one line at most 113 characters, anchor at least 10, append at most 462 characters and two lines), anchors (resolve, exactly once, shared or prefix anchors within one document — a pair's two ends share the item's line by design, so the rule runs per document), order (replaces in line order, appends last — pairs follow their `documents` order), wording (t1v2's filter-field, harm-frame and weakening lists and the nonce scan, imported, with the token appended as t1v2 does), the token, and for pairs the constraints of `cross-document-items-v0.md` section 3: the shared item's entry name on both documents, the eligible combination (the three of the packet's section 7 rule 5, verified as the v7 state's shared lines by a test), equal values after the entry name and changed from the old, the value format (a contact `<role words>, #<channel>`; a label or path a backticked name `in` a backticked `configs/<dir>/<file>.yaml`), no purely numeric change, host tokens unchanged, and zero occurrences of the new value in the document file. Each class has a test. An item that fails is reported by id and class in `results-mechanical.json` — the mechanical part of the packet's section 8 layout, with ratings and recovery as nulls for Part 3 to fill — and is converted nowhere: the reader's and the application's inputs carry valid items only.

**Pairs (decision 5).** A pair converts to the reader's four-place form (`stripped-pairs.json`: `pair_id`, `documents`, two statements each with its own `document`, `op`, `anchor_or_region`, `text`) and to two-statement application payloads each with its document (`payloads-pairs.json`, the `documents` field and per-statement `document`). The pair extension in the reader, the rater strip, the application module and the dry run (the INDEX's open item 4, the four places) is still the named prerequisite for reading, rating or planting a pair; this converter produces the forms now, and the load smoke test runs on the one-document arm, which needs none of them.

**The final message.** `extract` reads a writer's final message and takes the outermost JSON object with an `items` list; no parse, and every item of that writer-round counts as written and not valid, the text kept by hash (the launch notes section 2).
